# FloorVote Glossary

**Draft bill**: a bill a team tracks before it is officially filed; tenant-local, created by an admin, with no legislative data until linked.

**Link**: the admin action that folds a draft bill's engagement (votes, positions, comments, notes, custom fields, calendar events) into its filed bill and deletes the draft. Where both carry the same engagement, the filed bill's wins. Avoid: "merge" as the name of the action.

**Instance**: one organization's own FloorVote deployment, with its own data, people, and settings. Avoid: "tenant" in product copy; "site"; "workspace."

**Member**: anyone with a login in an instance, whatever their permission level. Avoid: "user" in product copy; "group member."

**Title**: the line shown under a member's name ("Senior Policy Analyst, Elections"), which the member sets on their Profile page and the instance stores as `users.title`, and also as `users.subtitle` until a later migration drops that column. Not a bill's title. For a superadmin it is kept in central and copied into the instance at each sign-in, so it is read-only there. Avoid: "subtitle," its name before #539, which survives only in the old column and the API aliases until they are removed; "role," "position," or "job title" in product copy.

**Permission level**: what a member may do in the instance: Owner, Admin, or Standard member. Avoid: "role," which means a named group (below).

**Owner**: the permission level that can do everything an Admin can, plus manage admins and owner-only settings.

**Admin**: the permission level that manages members, roles, notifications, and instance settings.

**Standard member**: the default permission level: follows bills, comments, and can be mentioned, with no administrative access. Avoid: plain "member" when contrasting with Admin.

**Role**: a named group of members that an admin defines, which can be @-mentioned together. Avoid: "group"; "team" when meaning a subset of members.

**@admins**: a built-in mention, open to every member, that notifies everyone who is an Admin or Owner when the comment is posted, in the app and by email, skipping the author and deactivated members. A person also mentioned directly or through a role is notified once, attributed to the direct mention, then the role, then @admins. Unlike a role, nobody creates or maintains it. Avoid: "admin role" (a role is a named group).

**Invite**: the email that brings a new member into an instance. Avoid: "invitation link" as the name of the email.

**Pending invite**: a member who was invited and hasn't signed in yet.

**Bounced invite**: a pending invite whose latest invite or sign-in email couldn't be delivered. Shown as "Email bounced." Avoid: "failed invite" (the email failed, not the invite); "undeliverable."

**Previously bounced address**: an address whose most recent delivery outcome from this instance was a bounce (a later delivery clears it), or that the email provider refuses to send to. Shown as "previously bounced." Avoid: "suppressed" in product copy.

**Provider**: where central gets a state's legislative data (LegiScan by default, or a legislature's own feed), and the adapter in `central/src/providers/` that reads it and maps it into central's shapes. Unrelated to the email provider. Avoid: "source" in code and copy, since it already means a calendar event's source and a bill's page on the legislature's site; "data source."

**State ownership**: which provider a state's legislative data comes from, one row per state in central's `state_providers` table, changed by an operator's claim. A state with no row is LegiScan's. A claim is refused while the state's current provider has tracked bills there, and only a cutover moves those. In central code and the admin API, a state's provider is its "owner," unrelated to the Owner permission level.

**Cutover**: moving a state that instances already track from its provider to another, run by an operator after a dry run. Each matched bill keeps its central row id, so its handle and every instance's copy of it stay as they are. Matched calendar entries keep their identities, and matched legislators their person ids. The new provider's first ingest of each bill sends no changes, and an undo puts the state back. Avoid: "migration"; "rekeying," which was #259's approach of rewriting each instance's bills.

**Partial snapshot**: a snapshot provider's answer that holds only the records changed since the ETag central handed it (`ProviderSnapshot.partial`). Central runs the pass on its stored records with those replacing the ones they name, and never removes a record one leaves out. It is valid only as an answer to a stored ETag: a partial snapshot answering a read in full fails the pass. Avoid: "delta" or "incremental sync," which suggest records can be removed.

**Bill handle**: a central bill's stable id as instances store it, in a tenant bill's `external_id` (for example `legiscan:123`, where `123` is central's bill row id). The `legiscan:` prefix is legacy and means "central bill," not where the data came from. The neutral form `bill:123` means the same central bill, and instances and central accept both (release sequencing is in the header of `shared/billHandle.ts`). Hearing UIDs are always built from the legacy form, never the neutral one, so calendars never churn. A bill's provider belongs on the bill itself, and a bill keeps its handle when its state changes provider. Build and parse handles only through the helpers (`shared/billHandle.ts` for the instance API and web app, `central/src/lib/billHandle.ts` in central). Avoid: "LegiScan id" for a handle; reading provenance from the prefix.

**Extra**: a field only one provider publishes (a DC law number, Maryland statute citations), declared in that provider's vocabulary with a label and display type and shown on the bill page in one "Additional information from <provider>" panel. Display only: a field that needs sorting, filtering, notifications, or AI, or that a second provider publishes, becomes a shared column instead. Avoid: "custom field," which is an instance's own field that members fill in.

**Relationship kind**: how one bill relates to another, the same across legislatures: **identical** (the same bill filed twice, usually one in each chamber), **package** (different bills the legislature moves together, such as Michigan's tie-barred bills), or **related** (anything else the legislature links, and any label the provider's vocabulary doesn't map). Each provider's vocabulary maps its own relationship labels to a kind, with per-state overrides, and central attaches the kind when it serves a bill's related bills. The bill page shows them as "Identical to," "Part of a package," and "Related," except that "Identical to" lists only identical bills outside the bill's companion group, which the page header already names, and has no entry when there are none. Avoid: "companion" for a kind (an identical companion is a bill whose relationship is `identical`); "type" for a kind, since a relationship's type is the provider's own label.

**Companion group**: the bills in an instance linked by `identical` relationships, named by either bill, including chains (A190 identical to S1713, and S1713 to S1714, makes one group of three), as corrected by an admin's group overrides. The team's engagement belongs to the group, but it is never moved: comments, votes, and notes stay on the bill where they were made, and reads resolve across the group. The group's comments interleave by time on every member's page, a member's vote and note are their most recent across the group, and each team field is the one set most recently on any member, except the analysis, which comes from a tracked member when one has an analysis (see **Team field**). A member's page shows a navy badge in its header for every bill in the group, its own first and each companion linking to its page, even for a group no provider relationship made. One muted line above the comments and position, "Comments, votes, and team position are shared with [A190]," names each companion as a mini navy badge, says "custom fields" too once the instance defines one, and uses the configured org noun; no field carries its own marker, and a bill in no group shows no line. Splitting a bill uses the same words. Splitting a group gives each bill back its own, with no data migration. Package and related bills are never grouped. Avoid: "merged bills," since every bill keeps its own record and page; "companion" for the group itself (a companion is one of its bills).

**Pulled companion**: a bill that didn't match the instance's keywords, in a companion group with a tracked bill, which the instance analyzes anyway so every bill in the group has its own summary and text. It joins by group membership only: its match type stays null, so it is never tracked and never a new match, and if the group splits it stays analyzed and untracked unless it matches on its own. Its analysis stays stored on it, but while it's grouped every member's page, its own included, shows the tracked bill's, even when the companion's is newer, until it matches on its own, no tracked bill has an analysis, or the group splits. An admin's Regenerate on a page re-analyzes the bill whose analysis that page shows, so on a pulled companion's page it re-analyzes the tracked bill, and the page says which bill it was. Nothing marks it. It is whatever is unanalyzed with no match type in a group that has a tracked bill (`api/src/lib/companionAnalysis.ts`). Avoid: "tracked companion" or "promoted" (promoting sets a match type).

**Group key**: a bill's `bills.group_key`, the smallest id among the bills in its companion group, or null for a bill with no identical companion in the instance. Only `api/src/lib/companionGroups.ts` writes it, recomputing groups on each delivery of a bill from central (and on each grouping by hand) from the identical relationships stored by handle in `bill_identical_links` and the group overrides. Reads find a group through `inGroupOf` there, never by comparing keys by hand.

**Group override**: an admin's correction of companion groups, made from the bill page's overflow menu and kept per instance as a pair of bills in `bill_group_overrides`: a `link` ("Group with…") groups the two as an identical relationship would, whatever the provider says, and a `split` ("Split from group", one pair with each other bill in the group) keeps the two apart even while the provider still names them identical. A split is a cannot-link: the two bills never share a group, so a bill whose relationships would bring them back together groups with neither, keeping only what an admin grouped it with by hand. It loses all its other identical companions too, even ones with no tie to either split bill, until an admin groups it. Every recompute reads them with the provider's relationships, so they hold through every sync. Grouping by hand joins the two bills' whole groups, and is refused when that would put two split bills in one group. Grouping a bill with one it was split from joins the two groups and clears every split between them, including splits made separately, by another admin or for another bill. Splitting takes the bill out of its whole group, and the rest follow their own relationships: bills only the split bill joined come apart, which the confirmation names first, and an admin can group them by hand. Grouping a split bill again joins it with the bill picked and that bill's group, not necessarily the whole group it left. Avoid: "manual link," which sounds like the draft bill's Link; "unlink" for a split.

**Group tags**: a bill's `bills.group_tags`, the tags of its companion group's current analysis (the tracked bill's, as **Team field** says), or its own tags when it's in no group. Every bill of a group has the same ones, so a tag filter and the tag facets test this one column, and a tag on a bill whose analysis isn't the group's never matches. Triggers keep it right whenever a bill's analysis, match type, or group changes, so nothing writes it by hand. Avoid: "tags" for this, which are the bill's own, from its own analysis.

**Claim source**: a claim from a bill's AI summary paired with a short quote from the bill text that supports it (and, for a PDF, the page it is on), asked for in the same analysis call and stored on the bill in `bills.claim_sources` (#568). It is pinned to the document the model read, which central's text route names, and a re-analysis replaces the whole list. Each item carries how its quote resolved (`status`: `exact`, `normalized`, `fuzzy`, `anchored`, `ungrounded`, or `unverified` for a PDF, whose text the instance never reads) and where, found at analysis time against `billHtmlToText` of the pinned document (`lib/claimResolution.ts`). A page shows its group's current analysis, which can be another member's, so claim sources are read through that analysis's bill (`readClaimSources`), never the page's own. Operators see counts of them by status per instance, and how many analyses stored none or were cut off inside them and retried without them (`lib/claimSourceCounts.ts`, read by central over the service binding). Avoid: "citation," which means a statutory citation the bill affects (`affected_citations`).

**Team event**: a structured record of a change to a bill's team-level state, one row per bill in `team_events`, with the actor (null when FloorVote did it automatically), a type, and per-type metadata. A companion group forming (`grouped`, which also lists the team field values it replaced) or splitting (`split`), each naming the bills joined or left, and a team field changing (`field_changed`: the field, and the group's old and new value) on the bill where it was set. Kept for the bill's own history, not the feed. Avoid: "feed event," which is the activity stream's row.

**Team field**: a value the team keeps per bill rather than per member: the official position, priority, custom field values, triage, and the team summary and tags from the AI analysis. A companion group shares them. Each stays stored on the bill where it was set, and every member's page reads the one set most recently on any member (`api/src/lib/teamFields.ts`), so setting one on any member's page sets the group's, triaging any member triages the group, and splitting gives each bill back its own. The analysis is the exception: a group shows the most recent analysis of a member that matches on its own (one with a match type), and only when no such member has one, the most recent of any member's, such as a pulled companion's. Clearing one clears it on every member. When bills with different values group, the older values give way, and the grouping event lists them. Avoid: "custom field" for all of them, since a custom field is one kind of team field.

**Grouping line**: the line a bill's comment thread shows where its companion group formed or split, set between the comments posted before and after. It appears only when it explains a change to the thread. One FloorVote made on its own appears only when a comment was posted, before the event, on a bill it joined or left (the event's `commentBills`, which the server reads from the comments table, so a split still names what left; a deleted comment or a deactivated member's doesn't count, and one at the very second of the event does, as the thread puts it above the line), and it names those bills: "Grouped with A190 as identical bills on October 11. Earlier comments on A190 now appear here." or "Separated from A190 on October 11. Comments posted on A190 no longer appear here." With no such comment it is left out, even from an empty thread. A line naming the admin who grouped or split by hand always appears ("Ada grouped this bill with S1713 on October 11."), with the comments sentence only when it applies. So does a grouping that replaced a team field value ("S1713's position, Oppose, was replaced by A190's, Support.") or undid splits, whoever made it. Read from the bill's own grouping team events.

**Group row**: the bill list's one row for a companion group (`api/src/routes/billsApi/groupList.ts`). Its first bill is the **lead**, the furthest along (ties by bill number), and the row's own fields are the lead's, while its team values, votes, and comments are the group's. Each bill's number and status stack in the cells the row already has, with identical statuses collapsed to one and, for a group larger than two, the lead, one other, and "+N". A bill with no companions is its own group and its row is unchanged. A filter matches a group through any bill in it, but a filter on a team field tests only the group's current value (a value a newer one replaced never matches), and every bill in the group meets it when that value does. The My bills and Unvoted scopes are the group's too: a group is in My bills when you have voted on, noted, or commented on any of its bills, even if the other filters meet only a different bill, and is out of Unvoted once you have voted on any of them. A bill with no companions is its own group, so both scopes test it alone. The bills that met every part of the filter are emphasized. The list's total, pages, sort keys (the furthest-along status, the latest last action, the group's current priority and position), "select all matching", and the 1,000 bulk cap all count and order groups, and the final tiebreak is the group key. Avoid: "grouped bill" for the row, since each bill in it keeps its own page.

**Stage**: the common step a bill's status belongs to, the same across legislatures: Introduced, In committee, Passed one chamber, Passed legislature, Failed, Vetoed, or Enacted. Each provider's vocabulary assigns its statuses to stages, so members can filter and compare bills across states whose status names differ. Stage is a grouping inside Status, not a second filter: where Stage is offered (some covered state's provider is not LegiScan, or a stage is already applied), the Status control lists its options under stage headings, most advanced first, with statuses that have no stage under "Other." A heading selects the whole stage and writes the `stage` parameter, and a status selects that status and writes `status`. On the server the two are one bill fact joined by OR: a bill matches when its status is a chosen status or its stage is a chosen stage, in the list, totals, facet counts, and bulk actions, and the status and stage facets both leave that whole fact out of their own counts. The facets response's `statusGroups` gives the page each status label's stage and rank. Avoid: "status" for a stage, since a status is the legislature's own term (DC's "Under Mayoral Review" is in the Passed legislature stage).

**Calendar entry kind**: what a bill's calendar entry is: a hearing, a markup (a committee acting on the bill, such as a mark-up or an executive session), a meeting, or a deadline (a date set in law for the bill's next step, not a meeting). Central sets it from the provider's vocabulary and sends it with every entry. Avoid: reading an entry's kind from its identity or type id.

**Calendar entry identity**: the key central keeps a bill's calendar entry under for as long as it exists, and that instances build its calendar UID from: the provider's own event id, or else the entry's kind, date, and description, never its position. LegiScan's entries keep the identity they always had (type and description). Changing an entry's identity makes every subscriber's calendar show it cancelled and recreated.

**Body event**: an event on a legislature's own calendar (a hearing, roundtable, mark-up, or meeting, with or without bills on its agenda), from a provider that publishes one, such as DC's Council calendar. Central keeps it under the provider's own event id, and a bill's calendar entry it covers is shown as the body event, so a hearing appears once. Avoid: "council event," which names one legislature's; "hearing without a bill" as the name, since a body event can have bills and can be a meeting.

**Date-field event**: a calendar event for the value of a date custom field on a prioritized bill, such as "Comment deadline: HB 12". It has the calendar source `field` and no kind, is never stored (the calendar, the feed, the dashboard count, and the week-ahead email read the bill's field value as they load), and can be changed only on the bill page. Avoid: "deadline" for it, which is a calendar entry kind that central sets from a legislature's own dates in law; "custom event," which an admin makes on the calendar itself.

**Capability**: what a state's data can do, from the provider that owns the state, such as body events or deadlines. Instances gate features on capabilities, never on a state's name.

**New match**: a bill that keyword matching brought into an instance and that no admin has triaged yet (set a priority or dismissed), at or above the instance's minimum relevance for new matches. Admins see new matches in the triage list and the "N new" chip, routine and bulk alike. A match stops being new once any bill in its companion group is triaged, because triaging one bill triages the group. Avoid: "new bill," which suggests the bill was just filed.

**Match provenance**: where a new match came from, declared by central when it links the bill to the instance and sent with the bill: routine or bulk. The instance keeps it with the match and on the matched event. A match with none (any match from before provenance existed) is bulk. Avoid: "source," which already means a calendar event's source and a bill's page on the legislature's site.

**Routine match**: a new match the regular sync made by finding a bill new to central, for an instance that already follows the bill's state (it holds links to bills of the state), such as a bill filed mid-session or prefiled for a new session. The only new matches that reach the digest and the feed.

**Bulk match**: a new match from anything that matches bills in bulk: a session seed, a keyword re-run, an operator import or backfill, an instance's first sync of a state it never followed, a provider cutover, or an existing monitored bill that starts to match. It stays in the triage list, where bulk dismiss handles it, and out of the digest and the feed. Avoid: "bulk event," which is a bulk edit's one feed event.

**New-matches row**: the feed's one summary row a day for routine new matches ("5 new bills matched your keywords"), shown to every member and expandable to the matched bills. It is a bill-less feed event of its own type, written when a routine match above the instance's minimum relevance is recorded (never for a bulk match or one with no provenance), so a match from before the row existed never appears. It lights the feed dot, and a matched bill that already has a priority keeps its normal card instead. Avoid: "new-match event," which is the per-bill matched event that only the analyzed feed scope lists.

**Notification**: one stored item in a member's notifications panel, telling them about an event on a bill's comments, of a kind (a mention, a reply, or a reaction). Written when the event happens, marked read when the member opens the panel or the bill, and hidden once its comment is deleted. Avoid: "alert"; "mention" for a notification of another kind.

**Muted bill**: a bill whose comments a member has muted, from the bill page or a reply email. It sends them no reply notifications, in the app or by email, but mentions on it (direct, role, @admins, or @everyone) still reach them. A member can mute a bill before ever commenting on it, unmute it from the bill page, and stays muted when a draft they muted is linked to its filed bill. A companion group is one conversation, so muting any of its bills mutes the group, and unmuting any of them unmutes it. Avoid: "unsubscribed," "unfollowed."

**Mute link**: the link in a reply email, signed for one member and one bill, that mutes that bill without signing in. It is both the email's one-click List-Unsubscribe and its "Mute this bill" footer link, which opens a page that asks before muting. It can mute nothing else and does not expire. Mention emails carry none.

**Keyword**: one line of an instance's keyword list, matched against a bill's title, abstract, and number. A bare word matches a whole word, `*` widens it (`election*`), and `#` stands for one digit. A list whose only entry is `*` matches every bill and sends all of them to AI, so it is a cost decision. Unrelated to `state_coverage`'s `["*"]`, which means every state. Avoid: "tag," which AI assigns from the instance's taxonomy, and "subject," which the legislature assigns.

**Subject**: a term a legislature assigns to a bill, shown on the bill page and filterable on the Bills page, grouped by state because each legislature's vocabulary is its own. An operator can hide a state's subjects with the `subjects_suppressed_states` config row. Avoid: "tag," which is the instance's own taxonomy applied by AI.

**Bill filter**: every filter on the Bills page at once (status, stage, year, state, position, priority, tag, subject, minimum relevance, search, custom fields, the four toggles, and the match mode), as one immutable value defined once in `shared/billFilter.ts`. Each filter has one name in every layer: the URL, a saved view, the API, the facets response, and the code. A custom field is `field.<slug>` in a query string, the search is `search`, and the API-only filter on a session's name is `sessionName`. It travels as a query string written by the shared `serialize` in one key order, so the URL, a saved view, a list request, a facet request, and a bulk action all carry the same string, and the web and the API read it with the same `parse`. Unknown keys and values are ignored, and there are no aliases for old names (`q`, `cf_<slug>`, `session`). Avoid: "filter state," "filter params," or "dimensions" for the whole value.

**Saved view**: a named, serialized bill filter and a sort order that an admin saves and every member sees in the view switcher. The view stores the filter's query string as the Bills page writes it, so it uses the bill filter's names, and a rename of a filter key rewrites stored views in a migration (0111 did so for `search`, `field.<slug>`, and `sessionName`). Applying one puts its slug in the address as `?view=`. Avoid: "preset"; "saved filter."
