2. Phase 1 — Cron decision tree

Runs hourly. Most ticks are no-ops; full passes (3×/day) and raw passes (7×/day) do the actual work. The cron is the LegiScan API gate — only matched bills are queued to the ingestor.

Cron quota cost

Per session: 3 full + 7 raw = 10 masterlist calls/day (~300/month). Across N active sessions × ~10/day each, this is the dominant fixed cost. The variable cost is getBill per matched-changed bill, typically a small fraction of total quota.

7. Known limitations

Durable properties of the current design, not a work queue. Each is verified against the code, not a historical note.

  • change_log fidelity for top-level fields. The cron pre-writes bills.title/status/description before queuing, so the ingestor's snapshot reads the post-change value and detectChanges never emits title_changed/status_change/description_changed for cron-triggered messages. Child-collection diffs (history, votes, etc.) are still captured correctly.
  • roll_call_votes gap. getBill returns vote summaries only, so live ingest never populates per-legislator vote rows; per-legislator records would need getRollCall calls. Bulk-seeded bills have them.
  • change_hash sentinel. The raw pass inserts new bills with change_hash = '', which forces a full update the next time the ingestor or full pass sees the bill. Cosmetic.
  • Monitoring-only latency. The raw pass doesn't notify stub bills, since there's no fresh metadata to deliver, so match_type=null bills update only on the full pass (~8h) while matched bills also update on the raw pass (~1h). That relies on the full pass seeing the change, which is why the raw pass deliberately leaves an unmatched bill's change_hash stale rather than advancing it. POST /admin/backfill-stub-actions/:tenantId exists to heal stubs affected before that behavior was in place.
